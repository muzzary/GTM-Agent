# GTM-Agent Implementation Plan

## Outcome

A user can submit any supported B2B product and ICP, approve researched
product claims, select from evidence-backed prospect recommendations, and
receive an evaluated personalized email generated by a fine-tuned model running
in Colab and imported through a validated inference-result bundle.

This plan implements `PROJECT_SCOPE.md`. Every phase ends with automated
checks, self-review, user manual verification, an atomic commit, and a push.

## Confirmed implementation boundary

- Products and ICPs are runtime inputs.
- B2B email is the first channel.
- Product claims require approval before use.
- The agent discovers/ranks prospects; the user selects one for deep research.
- Colab handles model benchmarking, training, evaluation, and real inference;
  the local application validates and imports reviewed result bundles.
- Permanent hosting and automatic email sending are post-MVP work.

## Phase 0 - Reproducible project foundation

**Proves:** The backend, frontend, tests, linting, secrets boundary, and CI can
run from a clean checkout.

**Builds on:** Approved scope.

**Tasks:**

- Select supported Python and Node versions.
- Add Python project metadata and a committed lockfile.
- Scaffold the FastAPI backend and React/TypeScript frontend.
- Add test, lint, format, and build commands.
- Add `.env.example`, configuration validation, and lightweight GitHub Actions.

**Acceptance:** A clean checkout installs from lockfiles and passes backend
tests/lint plus frontend tests/lint/build without real credentials.

**Manual gate:** Approve exact dependencies and run the smoke workflow.

## Phase 1 - Colab model, QLoRA, and inference-result feasibility

**Proves:** At least one permitted open model can satisfy the structured GTM
contract, complete a minimal QLoRA training smoke test on recorded Colab
hardware, and export a reproducible inference-result bundle.

**Builds on:** Phase 0.

**Tasks:**

- Define a fixed business-reasoning and structured-output benchmark with hard
  constraints, a review rubric, deterministic settings, and a tie-break rule.
- Benchmark exact candidate revisions for quality, JSON validity, unsupported
  claims, latency, GPU memory, license, and quantization compatibility.
- Record GPU, CUDA, Python, library, prompt, seed, and generation revisions.
- Run a minimal 4-bit load, LoRA attachment, one-step training, and adapter
  save/reload smoke test for viable finalists.
- Define the strict versioned inference request, response, and result-bundle
  contracts with request/revision identity and integrity hashes.
- Persist benchmark and inference artifacts incrementally outside the
  ephemeral Colab VM without notebook secrets or committed generated results.

**Acceptance:** On a recorded Colab GPU, at least one exact model revision
passes the benchmark hard constraints and QLoRA smoke test, produces a valid
hashed result bundle from real inference, and the local validator accepts that
bundle while rejecting malformed or mismatched bundles.

**Automated checks:** Strict contract and manifest validation, malformed model
output, missing metadata, revision/request mismatch, integrity failure,
duplicate import, and contract-compatible test-double tests.

**Manual gate:** Review candidate comparison and approve the base model.

**Risk gate:** If no candidate passes both inference and minimal QLoRA
feasibility on the recorded Colab hardware, stop and revise the model or
compute boundary before downstream model integration.

## Phase 2 - Structured backend walking skeleton

**Proves:** A product/ICP input can pass through every backend stage using
fixtures and produce a traceable draft without live research or model access.

**Builds on:** Phases 0-1.

**Tasks:**

- Implement campaign, product, ICP, claim, prospect, evidence, positioning,
  outreach, evaluation, approval, and trace schemas.
- Implement workflow states and legal transitions.
- Add deterministic fixture services for research, ranking, and generation.
- Expose the minimal FastAPI campaign workflow.

**Acceptance:** An API test creates a campaign, approves fixture claims,
selects a fixture prospect, and produces a validated draft plus complete trace.

**Automated checks:** Schema boundaries, state transitions, serialization,
approval enforcement, and fixture end-to-end tests.

**Manual gate:** Review data contracts, workflow states, and trace structure.

## Phase 3 - Product onboarding and claim approval

**Proves:** A user can configure a product/ICP and control which researched
claims are allowed downstream.

**Builds on:** Phase 2.

**Tasks:**

- Build the React/TypeScript product and ICP form.
- Validate form input in both frontend and backend.
- Add product-profile proposal and evidence display.
- Add approve/reject/edit actions with an audit record.
- Enforce that pending or rejected claims cannot enter later stages.

**Acceptance:** A user submits two different product/ICP configurations,
reviews proposed claims, and cannot continue until claim decisions are valid.

**Automated checks:** Form validation, API validation, approval-state,
authorization-boundary, and downstream claim-filter tests.

**Manual gate:** Complete onboarding for two contrasting products.

## Phase 4 - Multi-source prospect discovery and research

**Proves:** The agent can collect permitted public evidence across structured
sources, approved market seeds, and official company sites; discover and rank
matching companies; and deeply research a selected prospect before positioning.

**Builds on:** Phase 3.

**Tasks:**

- Implement provider/source policy, robots handling, URL/DNS/redirect
  validation, rate limits, timeouts, bounded parsing, privacy filtering, and
  caching.
- Store publisher, source category, canonical/retrieval URLs, policy/license
  basis, timestamps, hash, excerpt, evidence type, and collection status.
- Treat retrieved text as untrusted data and isolate it from destinations,
  source policy, tools, and agent instructions.
- Discover candidates through Wikidata/MediaWiki and approved public market
  seeds, then inspect bounded official-site pages for evidence-backed ranking.
- Keep discovery score, evidence quality, research completeness, uncertainty,
  conflicts, and unknowns separate and cited.
- Display candidate evidence and let the user select a prospect.
- Add a separate selected-prospect research stage for official products,
  services, projects, documentation, newsroom, initiatives, and configured
  public market sources.
- Require a completed provenance-valid prospect research profile before
  positioning or outreach can continue.

**Acceptance:** Fixture and approved multi-source live runs produce ranked
prospects with evidence; a selected prospect reaches `prospect_researched` only
after bounded deep research; blocked sources, incomplete research, and
unsupported ranking claims fail explicitly without enabling positioning.

**Automated checks:** Provider routing, source/robots policy, SSRF boundary,
redirect, privacy, cache, hash, rate-limit, citation, ranking,
fact/inference/conflict/unknown, deep-research completeness, workflow gate,
prompt-injection fixture, and unsupported-claim tests.

**Manual gate:** Review live source behavior, select a prospect, inspect its
deep-research profile, and confirm positioning remains gated until completion.

### Required Phase 4 follow-up before Phase 5

**Implementation status:** Implemented and accepted after manual verification.

Phase 4 is accepted as a bounded research workflow, with these usability and
targeting requirements implemented before outreach baselining:

- Add one or more intended regions to the ICP form and contracts. Discovery
  must treat selected regions as prospect-eligibility constraints, cite the
  evidence used to establish location, and keep unsupported geography explicit
  rather than inferring it from a company name or website domain.
- Improve selected-company feature coverage through broader permitted page
  discovery and source types. Missing capabilities, offerings, projects, or
  market signals must remain `unknown`; absence of collected evidence must not
  be presented as evidence of absence.
- Add a plain-language research presentation with familiar labels, short
  findings, and clearly separated unknowns and limitations. Keep the complete
  technical provenance, citations, and collection warnings available as an
  expandable audit layer instead of making them the primary human report.
- Translate and summarize non-English source material through an optional
  authenticated Colab model endpoint. Preserve original excerpts and expose
  source language, summary language, and translation status; model downtime
  must never be presented as a successful translation.

**Follow-up acceptance:** A region-scoped campaign excludes unsupported or
out-of-region candidates from the eligible result set; a reviewed company
profile distinguishes found facts from unknown fields; and a non-technical
reviewer can explain the report's main findings without reading raw evidence.

### Deferred research-workspace UX refinements

These refinements do not block the Phase 4 research proof and should be handled
with the next user-interface pass:

- Add campaign-aware navigation from the researched-prospect view back to the
  campaign's prospect list without losing the active campaign or research run.
- Limit each primary research section to three to five outreach-relevant points
  covering fit, likely need, useful trigger, and supported personalization.
- Keep full excerpts, citations, provenance, collection warnings, and technical
  details available in an expandable evidence view rather than discarding them.

## Phase 5 - Baseline outreach, traces, and evaluation harness

The CRM and revenue extension is planned separately in
[`docs/CRM_MVP_PLAN.md`](CRM_MVP_PLAN.md). It will connect the outreach
workflow to companies, contacts, deals, agent-callable CRM tools, and revenue
events without changing the existing research contracts.

**Proves:** The prompt-only model produces measurable outputs before training,
and every decision can be inspected.

**Builds on:** Phases 1-4.

**Tasks:**

- Define the generation prompt and structured response contract.
- Build the initial product/ICP generalization benchmark matrix.
- Record prompts, tool calls, evidence IDs, approvals, model revision, latency,
  retries, and outputs.
- Implement deterministic factuality and approved-claim checks.
- Save a reproducible prompt-only baseline report.

**Acceptance:** The base model completes the held-out benchmark and produces a
versioned report with traces, supported-claim metrics, and failure examples.

**Automated checks:** JSON validity, evidence support, claim approval,
trace-completeness, retry-limit, and benchmark reproducibility tests.

**Manual gate:** Review representative successes and failures.

## Phase 6 - Reviewed dataset and one outreach adapter

**Proves:** A reviewed, leakage-safe dataset and LoRA/QLoRA adapter improve
defined outreach behavior without weakening factuality.

**Builds on:** Phase 5.

**Tasks:**

- Audit permitted public business/outreach datasets and their licenses.
- Set a reviewable pilot size after inspecting the baseline and available data;
  cover multiple products and ICPs, then expand only when coverage or learning
  curves justify it.
- Label source, generation method, reviewer status, and quality dimensions.
- Split by product/company/prospect identity to prevent leakage.
- Train and version one outreach adapter in Colab.

**Acceptance:** Training completes and the held-out base-versus-adapter report
shows whether quality improved, regressed, or remained unchanged.

**Automated checks:** Dataset schema, license/provenance presence, duplicate and
split leakage, configuration, and evaluation regression tests.

**Manual gate:** Approve dataset quality and compare blind output samples.

## Phase 7 - Campaign evaluator, revision, and shadow comparison

**Proves:** The evaluator detects known flaws, bounded revision improves weak
drafts, and base-versus-adapter behavior remains observable.

**Builds on:** Phases 5-6.

**Tasks:**

- Encode the 1-5 rubric for relevance, clarity, differentiation, credibility,
  CTA quality, and brand fit.
- Combine deterministic checks with model-assisted scoring where justified.
- Add deliberately flawed examples and human-rated references.
- Implement bounded revision with explicit stop reasons.
- Run base and adapter outputs in shadow comparison without mixing results.

**Acceptance:** The evaluator flags known defects, reports false praise and
false criticism, and revision never bypasses approved claims or retry limits.

**Automated checks:** Rubric range, flaw detection, evidence preservation,
bounded-loop, evaluator consistency, and shadow-routing tests.

**Manual gate:** Compare evaluator scores with human ratings.

## Phase 8 - End-to-end agent runtime and web workflow

**Proves:** The complete form-to-approved-draft workflow operates with
controlled tools, visible state, and a validated Colab result handoff.

**Builds on:** Phases 2-7.

**Tasks:**

- Connect frontend, FastAPI runtime, evidence store, tools, and the validated
  inference-result importer.
- Enforce claim, prospect, and final-draft approval gates.
- Add pending-inference state, request/revision matching, idempotent bundle
  import, and resumable campaign state.
- Display traces, evidence, evaluation reasons, and actionable errors.
- Add final draft export without sending.

**Acceptance:** A user can configure two different campaigns, export a model
request, run it in Colab, import the validated result bundle, and complete the
workflow; a missing or invalid bundle remains resumable and cannot create an
unsupported draft.

**Automated checks:** End-to-end mocked tests, API/UI contracts, failure paths,
approval gates, idempotency, resume behavior, and export tests.

**Manual gate:** Complete the full workflow with a real Colab-generated bundle.

## Phase 9 - Reproducible evaluation package and release

**Proves:** Another engineer can reproduce the project, inspect its evidence,
and understand its limitations.

**Builds on:** Phase 8.

**Tasks:**

- Complete setup, architecture, model/data cards, limitations, phase log,
  failure analysis, and evaluation reports.
- Run the product/ICP generalization matrix and final regression suite.
- Measure Colab generation latency, GPU memory, bundle validation, and runtime
  failure behavior.
- Verify the repository contains no secrets, private data, model weights, or
  unreviewed artifacts.

**Acceptance:** A clean checkout follows the README, runs the documented Colab
inference demonstration, imports its reviewed result bundle, and reproduces the
documented workflow and reports.

**Automated checks:** Full backend/frontend suites, lint, build, secret scan,
artifact checks, notebook checks, and CI.

**Manual gate:** Final walkthrough and limitations review.

- Google account with Colab GPU access and sufficient compute availability.
- Optional model-repository account with accepted model terms.

- Permitted business outreach, marketing, and product-selling datasets.

- Windows laptop for development, tests, frontend/backend, and orchestration.

- Persistent remote storage for model weights and adapters; exact capacity is

## Risks and controls

- **Variable Colab compute:** Record hardware/runtime details and require both
  inference and minimal QLoRA feasibility before model approval.
- **Manual model handoff:** Validate request identity, revisions, schema, and
  hashes; keep pending campaigns resumable until a valid bundle is imported.
- **False generality:** Evaluate across multiple product categories and ICP
  patterns, not one scenario.
- **Source safety:** Public does not automatically mean permitted. Validate
  destinations, source rules, rate limits, and retrieved content.
- **Prompt injection:** Treat web content as untrusted data and keep tool
  permissions outside model instructions.
- **Dataset leakage:** Split by product, company, and prospect identity.
- **Evaluator bias:** Use deterministic checks, flawed fixtures, and human
  agreement instead of model judgment alone.
- **Dependency sprawl:** Add only what a phase acceptance test needs.

## Explicitly out of scope

- Automatic email sending, CRM integration, mass outreach, and production
  deployment.
- Permanent model hosting during the MVP.
- Training a foundation model or multiple adapters before proving one.
- Paid LLM APIs as a required path.
- Private datasets, unnecessary personal data, or conversion claims.
- Additional outreach channels before the B2B email workflow is complete.
